Unidade 3.1- Fundamentos de SegurançaAutenticação: Verifica se o usuário diz ser quem é.Autorização: Verifica as permissoes de acesso do usuario    Função Hash (Message Digest):             Basicamente um algoritmo que produz        uma sequencia diferentes para cada entrada e de tamanho fixo,        NAO REVERSIVEIS.        Pra verificar se uma senha é correta, o sistema armazena o hash da senha,        e compara o hash da senha digitada com o hash armazenado!        Hash mais usado é o SHA-256, que produz um hash de 256 bits (32 bytes).    Codificacao Base64:        Algoritmo utilizado para converter/codificar dados binários ou mais complexos em textos simples,        e vice versa. Muito utilizado na internet pois varios protocolos aceitam apenas dados em texto        como email e http. É usado em conjunto cmo o padráo MIME. E conseguimos sem senha sem nada        voltar a decoficar o texto para o formato original. Por isso nao é criptografia e só passagem!    Infraestrutura de chaves publicas (PKI):        Conjunto de tecnologias, políticas e procedimentos para criar, gerenciar, distribuir, usar e         revogar certificados digitais e chaves criptográficas.        O objetivo é garantir a segurança das comunicações eletrônicas e a autenticidade das partes envolvidas.                Conceitos:            -ICP: Infraestrutura de Chaves Públicas, é o conjunto de regras, políticas e procedimentos para criar, gerenciar, distribuir, usar e revogar certificados digitais e chaves criptográficas.            -AC Raiz - Autoridade Certificadora Raiz: Estabeleza a cadeia hierarquica de certificados. Estabelece            a politica, controla certificados de Acs e matnem a lista de certificado revogados.            -AC Autoridade Certificadora: Responsavel pore emitir, distribuir, revogar e gerenciar certificados digitais.            -Certificado Digital: Documento eletrônico que vincula uma chave pública a uma identidade, reconhecida pela ICP, como um nome de pessoa ou organização. Ele é emitido por uma autoridade certificadora e contém informações como o nome do titular, a chave pública, a data de validade e a assinatura digital da autoridade certificadora.            Esse certificado serve para envio de mensagem!        Calma, vai fazer sentido em baixo:            Criptografia de Chave Simétrica:                Custo barato!                Utiliza a mesma chave para criptografar e descriptografar os dados. É rápida e eficiente, mas o desafio é a distribuição segura da chave. Exemplos: AES, DES.            Criptografia de Chave Assimétrica:                Custo caro!                Utiliza um par de chaves: uma chave pública para criptografar os dados e uma chave privada para descriptografá-los. É mais segura para a troca de chaves, mas é mais lenta que a criptografia simétrica. Exemplos: RSA, ECC. Por isso temos par de chaves um publico e outro privado, o publico é para criptografar e o privado para descriptografar, e só o dono da chave privada tem acesso a mensagem.        Certificacao digital - ENVIO DE MENSAGEM:            Funciona assim: Em vez de eu pegar um documento inteiro e usar criptografia assimetrica, com as chaves publicas e privadas, eu vou primeiro gerar uma chave simetrica, vou criptografar esse documento com essa chave pq é um processo barato para documento pesado, ai vou usar a criptografia assimetrica para criptografar SOMENTE a chave simetrica, ai eu pego o doc criptografado a chave simetrica criptografada e passo pra quem eu quero enviar. Lembrando que a chave simetrica foi criptografada de forma assimetrica            com a chave publica de quem eu quero enviar, entao somente o destinatario com a chave privada correspondente vai conseguir descriptografar a chave simetrica e depois usar essa chave simetrica para descriptografar o documento. E é assim que funciona o envio de mensagem usando certificação digital!Unidade 3.2- Autenticação no Protocolo HTTPA autenticacao no http e um processo para verificar a identidade do usuario de uma aplicacao web.    Esquemas de autenticacao:        -Usuario anonimo + forms da aplicacao (Login)        -Autenticacao Basic        -Autenticacao Digest        -Autenticacao Bearer (Token authentication)        Autenticacao Basic:        Assim que o cliente tenta acessar algum recurso protegido, vai tomar de cara 401 Unauthorized, e no cabeçalho da resposta vai ter um campo chamado WWW-Authenticate: Basic, ai o cliente tem que responder com o campo Authorization: Basic        O cliente envia as credenciais (nome de usuário e senha) codificadas em Base64 no cabeçalho da requisição HTTP!         Recomenda-se utilizar apenas em conexoes HTTPS!!        exemplo: quando voce faz login no roteador, ele usa a autenticacao basic, e o nome de usuario e senha ficam codificados em base64 no cabeçalho da requisicao, e o roteador decodifica isso para verificar se as credenciais estao corretas.        Autenticacao Digest:        Cliente e servidor nao trocam mais senhas, e sim apenas o HASH!        -Autenticacao Bearer (Token authentication):        A autenticacao mais moderna e usada atualmente.         O cliente envia requisicao com sua senha, o servidor vai validar essa senha, se estiver tudo ok,        o servidor gera um token (uma string aleatoria) e envia de volta para o cliente, e o cliente vai usar esse token para acessar os recursos protegidos, e o servidor vai validar esse token para garantir que o cliente tem acesso aos recursos. O token tem um tempo de validade, e depois disso ele expira e o cliente precisa fazer login novamente para obter um novo token.Unidade 3.3- Json web token (JWT):Padrao que define uma forma compacta e segura de transferencia de informacoes baeadas em tokenno formato json (RFC-7519), utilizado em mecanismos de autenticacao e autorizacao.    Estrutura bsica da token JWT:        [HEADER].[PAYLOAD].[SIGNATURE]                Header: Informacoes sobre o tipo do token e o algoritmo de criptografia.        Payload: Informacao propriamente dita, Dados (claims) que podem ser reservados, publicos ou privados.        Signature: Assinatura do token que envia alterações. (So o gerador consegue validar se o token e verdadeiro!)        Campos reservados (claims):        -Iss (Issuer): Identifica o emissor do token.        -Sub (Subject): Identifica o assunto do token, ou seja, a entidade a qual o token se refere.        -Aud (Audience): Identifica o destinatário do token.        -Exp (Expiration Time): Define o tempo de expiração do token.        -Iat (Issued At): Indica o momento em que o token foi emitido.        Exemplo fluxo:            Navegador manda os dados de login, o servidor verifica se ta tudo ok, encima desses dados,            ela emite a jwt, assina o token e despacha pro cliente, o cliente entao vai submeter as proximas requisicoes o token, ai sim o servidor vai validar o token para garantir que o cliente tem acesso aos recursos protegidos.        Podemos validar o JWT pelo JWT.io, onde da pra ver o header payload real (pq nao ficam criptografadas) e tambem a signature!        Relacao mais comum entre JWT E Bearer token:            “estou usando autenticação Bearer com um token JWT”. Basicamente, o JWT é o formato do token que está sendo usado para autenticação Bearer. O cliente envia o token JWT no cabeçalho Authorization usando o esquema Bearer, e o servidor valida esse token para conceder acesso aos recursos protegidos.Unidade 3.4.1 - Open Authorization 2.0 (OAuth)Framework mais utilizado para empresas na internet.Foi criado para autenticação e autorização de recursos na web.    Caracteristicas:        -Evita exposicao de senhas        -Baseado no uso de tokens e autenticação Bearer        -Facilita a interoperabilidade (WEB, MOBILE, SERVER)        -Controla a velocidade e o escopo de acesso concecido.    OAuth - Papeis:        -Dono do recurso: Dona do material e conteudo.        -Aplicacao do cliente: aplicacao que vai fazer uso dos recursos.        -Servidor de recursos: mantem os recursos        -Servidor de autorizacao: onde mantem credencial, o que fazer e quem tem acesso ao tao recurso. (Google accounts, Facebook auth, etc)    Basicamente a gente pede autorizacao e o servidor de autorizacao vai validar    e retornar um token pra gente consultar os recursos em si.    OAuth - Access Token:        -É uma credencial para acesso a um recurso protegido.        -Trata-se de uma string em formato especifico de acordo        com a aplicação em questão.        -Uma acess token é obtida de acordo com o tipo de autorização.        -O acess token substitui a necessidade de usuario e senha!    OAuth - Tipos de autorização:        -Código de autorização(Authorization Code): Aplicacao cliente é uma aplicacao web ou nativa e mantem uma chave secreta. O Site x acessa seus dados do facebook        -Autorização implicita(Implicit Grant): Aplicação Cliente é baseada no browser e não pode        manter uma chave secreta. Exp: Aplicações SPA(Single Page web)        -Credenciais do usuario(Resource Owner Password Credentials): Aplicacao criente        é a proxima do servidor de autorização e requer usuario e senha, normalmente, ambos feitos pela mesma empresa. Exp: Aplicativo gerenciador de negocios do facebook. (Ele pode interagir diretamente pegando usuario e senha, e recebendo assim o token de autorizacao/acesso)        -Credencias do Cliente(Client Credentials): Aplicação cliente é a proprietária dos recursos e não o usuari final: Exp: Cloud Azure acessando dados em storage interno.(A aplicacao do cliente é ela que vai fazer autorização e acesso por estar no mesmo ambiente.)Unidade 3.4.2 Open Authorization 2.0 (OAuth) - 2:Fluxos de autorização implicita:é basicamente como funciona fazer login com o google, facebook, etc. O cliente (aplicação) redireciona o usuário para o servidor de autorização, onde ele faz login e concede permissão para a aplicação acessar seus dados. O servidor de autorização então redireciona o usuário de volta para a aplicação com um token de acesso na URL. A aplicação pode então usar esse token para acessar os recursos protegidos em nome do usuário.        O refresh token aqui é um pouco diferente, ele é um token que é usado para obter um novo access token quando o access token atual expira. Ele é emitido junto com o access token e tem um tempo de validade mais longo. Quando o access token expira, a aplicação pode usar o refresh token para solicitar um novo access token sem precisar que o usuário faça login novamente.         Entao pra conseguir o refresh token, a aplicação precisa solicitar explicitamente durante o processo de autorização, e o servidor de autorização precisa estar configurado para emitir refresh tokens. Nem todos os fluxos de autorização suportam refresh tokens, então é importante verificar a documentação do servidor de autorização que você está usando para ver se eles são suportados e como solicitá-los corretamente.                Imagine o seguinte, fiz login, e em algum momento ao tentar acessar o recurso        o token inicial expirou, eu faço o que? Eu uso o refresh token para solicitar um novo access token, e ai sim eu consigo acessar o recurso novamente sem precisar fazer login de novo. E é assim que funciona o refresh token no fluxo de autorização implicita do OAuth 2.0!!Unidade 3.4.3 Open Authorization 2.0 (Controle de acesso):Sempre posso e devo conseguir controlar e remover aplicacoes de autenticacao que deixam habilitados logins de terceiros, como google, facebook, etc. E isso é importante para manter a segurança da minha conta, pois se eu tiver uma aplicação que eu não uso mais ou que eu não confio, eu posso revogar o acesso dela e garantir que ela não tenha mais acesso aos meus dados. E isso é algo que deve ser feito regularmente para manter a segurança da minha conta e dos meus dados pessoais!Unidade 3.5 Cross-Origin Resource Sharing (CORS):Mecanismo de segurança sobre http que permite paginas de um site Aacessam recursos de um site B.    A politica de mesma origem (same-origin) restringe sites de acessarem recursos apenas no servidor em que está hospedado, evitando que codigos maliciosos usem chamadas AJAX para repasse de informacoes em uma sessao aberta.    O cors é basicamente relaxar essa politica de mesma origem, permitindo que um site acesse recursos de outro site, desde que o servidor do outro site permita isso. O servidor do outro site pode permitir isso através do cabeçalho Access-Control-Allow-Origin, onde ele especifica quais origens são permitidas acessar os recursos. Por exemplo, se o servidor do site B permitir acesso ao site A, ele vai incluir o cabeçalho Access-Control-Allow-Origin: https://siteA.com na resposta HTTP, e assim o site A vai poder acessar os recursos do site B.    O COrs define dois tipos de requisicoes:        1- Requisicao simples: GET, HEAD POST, MAIS TRANQUILO, VERIFICACAO REQUISITADA.            Nos recebemos o site de um servidor a, vamos para o servidor b, o b vai validar e vai ver, o site a pode requisitar? pode, entao vai passar um cors pro site a, e ai sim o site a vai conseguir acessar os recursos do site b.        2- Requisicao preflight: PUT, DELETE, PATCH, MAIS RIGOROSA, VERIFICACAO OBRIGATORIA via metodo OPTIONS.            Recebemos site do a, vamos pro b, antes de mandar a requisicao, mandamos um options, hostb vai validar, vai retornar, o site a ta autorizado!, ai o navegador envia a requisicao pro a e recebemos e ta autorizado    Tem como desabilitar o CORS, mas isso nao é recomendado, pois ai qualquer site poderia acessar os recursos do seu servidor, o que pode ser um grande risco de segurança. O ideal é configurar o CORS corretamente para permitir apenas as origens confiáveis acessarem os recursos do seu servidor, e assim garantir a segurança da sua aplicação e dos seus dados.
